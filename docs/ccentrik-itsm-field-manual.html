ccentrik ITSM Field Manual

A working developer's guide to this specific codebase — every explanation traced to a real file, function, entity and HTTP request. Written so that after reading it you can change this application, debug it, and explain it to someone else.

How to read the evidence markers

Claims in this book are labelled, so you always know what is fact and what is inference:

  • Verified — I ran it. A real HTTP request against a real server, or a real database query. The observed output is shown.
  • Read from code — traced by reading the source, not executed. Accurate but unproven.
  • Risk — a defect or hazard I can demonstrate or point at precisely.
  • Not present — you may expect this; it does not exist in this codebase.

How the verified facts were produced: I copied the schema to a throwaway SQLite database, deployed the current db/schema.cds to it, ran the CAP server on port 4005 (your teammate's server on 4004 was never touched), and drove the full ticket lifecycle with curl as the real mocked users. Every "Verified" marker traces to one of those runs.

Chapter 01

Application Overview

What this application is, in terms of its own code.

This is an internal IT service management (ITSM) tool for ccentrik, an SAP services company. Employees at client organizations raise tickets; a service desk triages and assigns them; consultants resolve them; the requester confirms and closes them. A separate platform admin manages which client organizations exist and how the app is branded for each.

Concretely, the codebase is two applications joined by one HTTP contract:

HalfRuns whereRoot fileLanguage
SAPUI5 frontendBrowserapp/webapp/index.htmlJavaScript + XML views
CAP backendNode.js (Cloud Foundry or local)srv/service.jsJavaScript + CDS

The contract between them is a single OData V4 service, ITSMService, mounted at /odata/v4/ITSMService/. Everything the browser knows about the database, it learns through that URL.

The four personas

These are not invented for this book — they come from srv/service.js's onCurrentUser() and xs-security.json's role templates. Verified

If you understand those two plus Main.controller.js, you understand roughly 70% of the application's behaviour.

What this application does not have

Naming absences early saves you hunting for them later. Not present

  • No comments feature. There is no Comment entity and no comment UI. The nearest thing is TicketLog, a fixed four-row workflow audit trail — see Chapter 29.
  • No password reset / user provisioning. Creating a "user" in the Admin panel writes a User row only; a working login still requires package.json (local) or an identity provider (production).
  • No SLA engine. OrganizationSLA exists in the schema with no seed data, is not exposed by the service, and is read by no code. dueAt is a plain field somebody types in.
  • No unit or integration tests. No test folder, no test script in package.json.
  • No i18n in practice. app/webapp/i18n/i18n.properties exists but no view binds to a resource model; all labels are hardcoded in the XML.
  • No annotations file. There is no annotations.cds and no Fiori Elements — every screen is a hand-written freestyle UI5 view.

app/webapp/index.html

Why it exists at all

Simple explanation: a browser cannot open a "UI5 app". It can only open an HTML page. index.html is the one page whose only job is to load the UI5 framework and then hand control to your code.

Why this project needs it: this file is hand-written, not generated by CAP or by a Fiori template. That has a practical consequence you will feel daily: cds watch's LiveReload does not inject into it, so a hard refresh (Ctrl+Shift+R) is required after any view, controller or CSS change.

Read from code The router starts late — on purpose

In most UI5 apps oRouter.initialize() is the last line of init(). Here it sits inside the .then() of _resolvePersona() (Component.js:47). Nothing renders until the server has answered "who am I". That is deliberate: route guards and the persona home page cannot be decided without the answer. The cost is that a slow /currentUser() means a longer blank screen.

What a UI5 Component is

Simple explanation: a Component is the object that owns your whole application — its models, its router, its manifest. Views and controllers reach it with this.getOwnerComponent(). Anything that must exist once, for everybody, belongs here.

Why this project needs it: three things in this app are global — who is logged in, what colours their organization uses, and which pages they may open. All three are resolved here, once, before any page appears.

The theming mechanism

--brand-fill              solid colour or a linear-gradient

What would break if you changed this file

  • Remove setModel(…, "role") → roleConfig.js receives undefined persona and silently falls back to END_USER; every non-End-User loses their buttons.
  • Move oRouter.initialize() out of the .then() → the first page renders before the persona is known; guards fire late and users flash the wrong screen.
  • Delete the .catch() in _resolvePersona() → any backend hiccup leaves the router never initialized, i.e. a permanently blank page.

Verified The rule that explains most of the code

Anything read from the server for display in a list or form uses OData binding. Anything computed in the browser goes into a JSONModel. The KPI tile counts are computed in JS from a downloaded ticket array — they are not $count queries. Same for every number on the Service Group dashboard.

Binding modes you will meet

  • List binding — bindList("/Tickets", ctx, sorters, filters, params). Feeds tables and requestContexts().
  • Context binding — bindContext("/Tickets(ticketID='INC-1')", …). One entity, used by _loadTicket().
  • Operation binding — bindContext("/ticketAction(...)"). The (...) suffix marks a deferred operation you must execute(). Used by _invokeTicketAction() and _resolvePersona().

Transient contexts — the create trap

Purpose

generateTicketIdentifiers(sTicketType)

srv/service.js:647

Purpose

Produces the next human-readable ticket number for a type, e.g. INC-00006.

Called by

onBeforeCreateTicket() only.

Step by step

normalise type: (sTicketType || "GENERAL").trim().toUpperCase()
        ↓
SELECT.one.from(TicketCounter).where({ type })
        ↓
   ┌── not found → INSERT { type, lastNumber: 1 }
   └── found     → lastNumber++ then UPDATE
        ↓
prefix = PREFIX_BY_TYPE[type]  (INCIDENT→INC, SERVICE_REQUEST→SRV,
                                CHANGE→CHG, PROBLEM→PRB)
         or type.slice(0,3) as fallback
        ↓
return { ticketID: "INC-00006", ticketNumber: "INC-00006" }

Data used

Entity itsm.master.TicketCounter — { key type, lastNumber }. One row per ticket type.

Risk Read-then-write race

The SELECT and the UPDATE are two separate statements with no lock and no uniqueness constraint on Ticket.ticketID beyond it being the key. Two simultaneous creates of the same type can read the same lastNumber; the second INSERT then fails on a duplicate key, or worse, succeeds if the first has not committed. In practice this project's traffic makes it unlikely, but it is a real defect, not a theoretical one. A fix is to make the counter update atomic (UPDATE … SET lastNumber = lastNumber + 1) and read the value back.

Note on ticketID and ticketNumber

They are set to the same string. The schema keeps both fields, and the UI shows ticketNumber while routing on ticketID. Nothing currently distinguishes them — if you ever want a stable internal key separate from a display number, this is the one function to change.

Why this exists — the beginner explanation

The view binds incident-form fields with a flat relative path such as {incidentForm/system}. UI5 sends that as a nested object inside the ticket's PATCH body, but without the child row's own key. CAP's generic handler cannot tell which IncidentForm row you mean, so it silently drops the change — no error, just nothing saved. This handler intercepts the nested object, removes it from the parent payload, and issues its own explicit UPDATE matched on ticketID.

What breaks if you change it

Delete this block and every category, impact, urgency and description edit on the ticket form stops persisting — silently. That silence is what made the original bug hard to find.

Note on req.params

req.params is an array of the keys along the request path. For PATCH /Tickets('INC-6') it is [{ ticketID: 'INC-6' }]. That is why const [oKey] = req.params then oKey.ticketID.

Beginner first: what CAP actually gives you

You write a .cds file describing entities and a service. CAP then generates a complete OData service — create, read, update, delete, filtering, sorting, paging, metadata — with no code. You only write JavaScript for the parts that are genuinely custom.

This project takes that seriously. Out of everything the service does, only three before handlers, one action and one function are hand-written. All list reads, all single reads, all deletes, and most of create/update are CAP generics.

Projections

Simple explanation: a projection is a view onto an entity. as projection on master.User exposes the whole entity unchanged. You could narrow it — as projection on master.User { userId, name } — to hide fields. This project narrows nothing.

Association vs Composition — the beginner explanation

  • Association = "points at". reportedByUser lets you write $filter=reportedByUser/client eq 'MERIDIAN' (the Dashboard's client filter does exactly that). The User has an independent life; deleting a ticket does not delete the user.
  • Composition = "owns". The child cannot exist without the parent. Deleting a ticket cascades to its incident form, attachments and logs. It is also why you can POST a ticket with a nested incidentForm in one request (deep insert).

All four are unmanaged — they carry an explicit on condition matching on ticketID rather than letting CAP generate a foreign key. That is what makes the deep-update problem in onBeforeUpdateTicket necessary.

The "all tiles show 0" bug — what it was and why the fix works

You hit this: change the tile selection, press Save, and every tile — including Total — dropped to 0, while the ticket table below still showed its rows.

The original code

.then(function (aContexts) {
    …setModel(good data)…          // correct counts land here
    that._syncTileClasses();       // ← could throw
    that._updateAssigneeOptions(aTickets);
})
.catch(function () {
    …setModel({ tiles: _buildTiles([]), categoryData: [] })…   // wipes it to zeros
});

Why it produced exactly that symptom

A .catch() chained after a .then() also catches errors thrown inside that .then(). So a rendering error occurring after the good data had already been set was misread as "the request returned nothing", and the recovery path overwrote correct counts with zeros. The ticket table was unaffected because it uses a separate binding that was never touched — which is exactly the pattern you saw in your screenshots.

The thrower was _syncTileClasses(): it walks tileRow's items and did oWrap.getItems()[0].getBindingContext(...) with no guard. Changing the tile set replaces the dash model, so the aggregation rebuilds, and a wrapper caught mid-rebuild yields undefined → TypeError.

What I verified while diagnosing it

The backend was ruled out first: the exact tiles query returns HTTP 200 with all four tickets, and the request is byte-identical before and after the save — the filters do not depend on tile selection at all. Verified.

The three changes

ChangeWhy it matters
sap/base/Log imported and Log.error("Could not load KPI tile data", oError) in the catchThe original catch swallowed the error entirely — no console output. That silence is what made the bug undiagnosable from outside. Now the real error is visible, and it uses the same logging convention as the project's other three controllers.
return null; instead of re-seeding zerosonInit already seeds zeroed tiles, so the catch's fallback was redundant on first load and destructive on every refresh. Returning null signals "no data this time" to the next .then(), which then skips the render follow-ups and leaves whatever is on screen intact.
if (!oTile) { return; }Tolerates an items aggregation that is mid-rebuild, so _syncTileClasses can no longer throw a TypeError into the data path.

The resulting structure

requestContexts()
  .then(  … set the dash model, return aTickets … )   // data path
  .catch( … Log.error, return null …            )     // errors from the read OR the data path
  .then(  if (!aTickets) return;                      // render path, past the catch
          _syncTileClasses(); _updateAssigneeOptions(aTickets); );

The principle worth carrying to other controllers: a recovery path must never destroy state that is already correct, and an error handler that logs nothing turns a five-minute bug into a five-hour one.

Search

onSearch: function (oEvent) {
  this._mFilters.search = oEvent.getParameter("query")      // Enter / search icon
                       || oEvent.getParameter("newValue")   // liveChange, per keystroke
                       || "";
  this._applyFilters();
  this._loadTiles();
}

The view binds both search and liveChange to this handler, which is why the single || chain reads two different parameter names.

Risk Every keystroke fires two OData requests

liveChange → _applyFilters() + _loadTiles(). Typing "printer" sends 14 requests, each re-reading the ticket list and recomputing every tile. There is no debounce. On a large ticket table this will be felt. The standard fix is a short timer:

onSearch: function (oEvent) {
  var sValue = oEvent.getParameter("query") || oEvent.getParameter("newValue") || "";
  clearTimeout(this._iSearchTimer);
  this._iSearchTimer = setTimeout(function () {
    this._mFilters.search = sValue;
    this._applyFilters();
    this._loadTiles();
  }.bind(this), 300);
}

The aging filter — an interesting piece of CQL

_agingFilters(sBucket) converts a bucket label into date-range filters on createdAt, e.g. "8-30 days" becomes two filters (createdAt < now-8d AND createdAt >= now-30d). It returns an array which _buildScopeFilters() concatenates.

Reset

onResetFilters() re-creates the whole _mFilters object, clears the four dropdowns, resets the tile selection state and the table title, then refreshes both the table and the tiles. Note it resets all fifteen keys, including ones no dropdown exposes — which is correct, since a drill-down may have set them.

Read from code Two silent degradations to be aware of

Two deployment traps this project has already hit

1. A leftover process command. If an app of the same name was ever pushed manually, cf deploy does not reset its start-command override or its environment variables. Chapter 39

What Happens When…

1. I open the application

Browser loads index.html → UI5 core from ui5.sap.com → libs sap.m, sap.ui.unified, sap.viz → ComponentSupport instantiates itsm.ui → manifest.json read → ODataModel created and $metadata fetched immediately (earlyRequests) → Component.init() → /currentUser() → role model, theme, guards → hash set to persona home → router.initialize() → view + controller → first data request. Nothing renders until /currentUser() answers.

2. I log in

Locally: the browser prompts for basic auth; package.json's mocked users validate it. In production: the approuter redirects to XSUAA, you authenticate at the IdP, a JWT with your scopes comes back, the approuter stores a session cookie and forwards the JWT to ITSM-srv on every proxied call. Either way the app's first meaningful call is currentUser().

3. The Dashboard opens

_onShow() → first-visit setup (_buildFiltersModel fires 3 lookup reads plus an Organizations read; _setupChart sets the viz palette) → _applyPendingFilter() consumes any stashed drill-down filter → _applyFilters() filters and refreshes the table binding → _loadTiles() issues one GET /Tickets that feeds tiles, donut and the assignee dropdown. An End User's request carries $filter=reportedBy eq '<id>'; everyone else gets status ne 'DRAFT'.

4. I click New Ticket

onCreateTicket() → navTo("create") → route matches → _onCreate() discards any stale transient context, sets _bCreateMode/_bEditing, calls bindList("/Tickets").create({status:"DRAFT", reportedBy, incidentForm:{}}), binds the view to that context and calls _refreshUiModel("DRAFT"). No HTTP request is made.

5. I submit a ticket

See Chapter 25 for the full twenty-step trace. Summary: submitBatch → POST /Tickets → onBeforeCreateTicket assigns INC-000NN → created() resolves → POST /ticketAction SUBMIT → role gate → status NEW, four TicketLog rows, two emails attempted → _loadTicket re-reads → MessageBox → navigate home.

6. Service Group assigns a ticket

Two requests. First PATCH /Tickets(id) {messageProcessor}, where onBeforeUpdateTicket stamps assignedAt. Then POST /ticketAction ASSIGN, which reads the consultant from the ticket row, marks the Service Group log Completed and the Consultant log Pending, sets status ASSIGNED/IN_PROGRESS, and emails the consultant. Order matters — see Chapter 21.

7. Consultant updates a ticket

Two-way bindings queue property changes on incidentGroup. Save → submitBatch → one PATCH. If any incidentForm/* field changed, onBeforeUpdateTicket pulls the nested object out and issues its own UPDATE/INSERT against IncidentForm matched on ticketID, because CAP's generic handler would otherwise drop it silently.

8. Status changes

Two different mechanisms. Lifecycle statuses (NEW/ASSIGNED/RESOLVED/CLOSED) come only from ticketAction, which also maintains the workflow log. Manual statuses (IN_PROCESS, CUSTOMER_ACTION, SOLUTION_PROPOSED, CONFIRMED) come from a Consultant picking the Status dropdown and saving — a plain PATCH, no log entry, no email. onStatusChange() also nulls subStatus so a stale pairing cannot survive.

9. I upload a document

Phase 1: one OData create per file through the ticket's attachments composition, then submitBatch. Phase 2: read the server-assigned IDs back off the ticket context, match by fileName+fileSize, and PUT each binary to …/attachments(ID='…')/content with fetch. Then _refreshAttachments() rebuilds the JSON model. See Chapter 28 for why two phases are necessary.

10. I add a comment

Not possible. No comment feature exists. The nearest data is TicketLog.remarks, which only ticketAction writes, with fixed strings.

11. I refresh the page

Full restart: bootstrap again, /currentUser() again, models rebuilt from scratch. Two things survive: the URL hash (so you return to the same route, and _onDetail re-reads the ticket) and localStorage's tile preference. Everything else — pending unsaved edits, transient create contexts, the stashed drill-down filter — is lost. An unsaved new ticket is gone entirely.

12. An OData request fails

Depends where. onSave/onSubmit/_runLifecycleAction: Log.error plus a MessageBox carrying the server's message when available. _loadTiles: Log.error and the current tiles stay put. _resolvePersona: silently degrades to an empty End User. _refreshAttachments: unhandled rejection, stale list.

13. The database is unavailable

CAP returns 500 on every data request. In the browser: /currentUser() fails → the catch makes everyone an End User with userName: "" → the dashboard filters on reportedBy eq '' → an empty table and zeroed tiles, with no error message. It looks like an empty account rather than an outage. In production the app also fails to start if HANA is down at boot — see Chapter 36.

16. I select/unselect KPI tiles

onManageTiles() builds the tp model and opens the dialog. Each checkbox fires onTilePickerSelectionChange(), which recounts and enables Save only at exactly six. onSaveTileSelection() writes _aTileKeys, persists to localStorage, closes the dialog and calls _loadTiles() — one fresh GET /Tickets, then recomputed counts. See Chapter 31 for the bug this flow used to have.

17. I apply a dashboard filter

onFilterChange() reads all four dropdowns into _mFilters, then calls both _applyFilters() (table) and _loadTiles() (tiles/donut). Two requests go out. The tiles use _buildScopeFilters(false) so they respect the new filter but not the status selection.

18. I search for a ticket

onSearch() is bound to both search and liveChange, so it fires on every keystroke, each time issuing two requests. The filter becomes an OR over ticketNumber contains X and shortDescription contains X. There is no debounce — see Chapter 32 for the fix.

Chapter 40

Problems Found in This Codebase

Only issues visible in the source. Nothing invented, each with evidence.

P1 — pendingWith / pendingWithName are written but do not exist Confirmed

WhatAll four ticketAction branches set these two fields; db/schema.cds declares neither.
WhyThe handler was written against a schema version that had them, or was pasted in from a branch that did. A later merge kept the handler and lost the fields.
Detectgrep -n pendingWith db/schema.cds → nothing. Then PRAGMA table_info(itsm_transaction_Ticket) after a fresh deploy → absent.
ImpactNot a crash. CAP silently drops unknown properties, so the action succeeds and the rest of the update lands. But "pending with" is never recorded, and Main.controller.js's comment about reloading pendingWith describes a field that never arrives.
FixAdd pendingWith : String; and pendingWithName : String; to entity Ticket, then npx cds deploy --to sqlite:db/itsm.sqlite.
PreventBefore merging a handler someone pasted in, grep the schema for every field it writes.

P2 — No entity-level authorization Confirmed

Covered in full in Chapter 19. Any authenticated user can read and write every entity by direct HTTP. This is a known team decision ("itna secured nahi rakhna"), recorded here so it is a choice rather than a surprise. The fix, if you ever want it, is a @restrict block per entity.

P3 — TicketLog is maintained but never displayed Confirmed

Every action carefully writes the four-stage trail; no view reads /TicketLogs. The most valuable audit data in the system is invisible. Fix is frontend-only: bind a table to the existing ticketLogs composition, sorted by SrNo.

P4 — Two email subsystems, the better one unused Confirmed

srv/utils/mail.js (lazy pooled transporter, config validation, HTML→text fallback, cds.log) is imported by nothing, while service.js uses a module-level transporter and console.error. Meanwhile seven designed HTML templates in email-templates/modern-card/ are referenced by nothing, and the three templates actually used are inline template literals. Three parallel implementations, one live. Consolidate onto utils/mail.js (Chapter 30 has the migration).

P5 — Resolve and Close send no notification Confirmed

service.js:490 and :554 are commented-out sends. The requester is never told their ticket was resolved, so they cannot know to close it. For a service desk this is the most important missing notification.

P6 — Search fires two OData requests per keystroke Confirmed

liveChange=".onSearch" with no debounce, and the handler calls both _applyFilters() and _loadTiles(). Chapter 32 has a three-line fix.

P7 — Ticket counter has a read-then-write race Confirmed

generateTicketIdentifiers() reads lastNumber, increments it in JavaScript, then writes it back. Concurrent creates of the same type can collide on the primary key. Fix: make the increment atomic in SQL and read back.

P8 — Four KPI tiles track statuses the workflow never produces Design mismatch

TILE_POOL offers IN_PROCESS / CUSTOMER_ACTION / SOLUTION_PROPOSED / CONFIRMED, but ticketAction only produces NEW / ASSIGNED / RESOLVED / CLOSED — and there is no tile for ASSIGNED or RESOLVED. The dashboard therefore looks empty on a perfectly healthy system.

P9 — createdByLocation and orgName are never written Confirmed

buildServiceGroupEmailTemplate() prints both into the notification email, but no code ever sets them, so the email shows undefined for Location and Organization. firstResponseAt is likewise never written yet is read by Main.formatSlaText().

P10 — description exists on both Ticket and IncidentForm Ambiguity

Ticket.description : String and IncidentForm.description : LargeString. The email templates read ticket.description; the form's "full description" field binds to the incident form's. Two fields, similar names, different owners — a classic source of "I saved it but the email is empty".

P11 — The committed local database is stale Confirmed

db/itsm.sqlite predates four schema fields. Anyone running against it gets undefined where the current code expects data. One command fixes it; worth doing before you debug anything else.

P12 — No client-side validation despite the error text Confirmed

onSave's failure message says "Please check the required fields", but nothing checks them and the backend enforces nothing either. A ticket with no type and no description saves successfully.

P13 — Attachment matching collides on identical files Minor

onFileSelected matches saved rows by fileName+fileSize; two identical files in one selection resolve to the same row.

P14 — Drill-down filters are not bookmarkable By design, worth knowing

The Service Group drill-down passes its filter through the Component instance rather than the URL, so reloading the filtered dashboard loses the filter and the page title.

Suggested order of work

The seven facts that explain most confusing behaviour

  1. Nothing is written until submitBatch("incidentGroup"). create(), property changes and delete() only queue.
  2. binding.filter() is a no-op if the filters are unchanged — always follow it with refresh().
  3. Deep-updating incidentForm needs the workaround in onBeforeUpdateTicket; without it CAP drops the change silently.
  4. ticketAction bypasses the before handlers because it writes with direct tx.run statements.
  5. Route guards and roleConfig are cosmetic. Only @requires and the action role gate are enforced.
  6. Email failures are invisible and never block anything.
  7. onInit() runs before the view is in the control tree — do byId() work in patternMatched instead.
